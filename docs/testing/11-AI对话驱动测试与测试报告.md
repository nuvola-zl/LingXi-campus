# 第一部分：AI 对话驱动的测试计划

## 能力边界

**AI 对话能做的（直接在聊天框完成）：**

| 操作 | 触发工具 | 最典型输入 |
| --- | --- | --- |
| 申领设备 | DeviceTools.requestDevice | 「我想申请一台 macbook_pro」 |
| 查申领进度 | DeviceTools.queryDeviceStatus | 「查一下 DEVxxx 的状态」 |
| 重复申领拦截 | DeviceTools.requestDevice → DuplicateChecker | 再问一次同样的，AI 会拦截 |
| 查空闲会议室 | MeetingRoomTools.findAvailableRooms | 「明天下午2点到4点有空的会议室吗」 |
| 预定会议室 | MeetingRoomTools.bookRoom | 「帮我预定明天下午的A会议室」 |
| 取消会议室预定 | MeetingRoomTools.cancelBooking | 「取消我的会议室预定」 |

**AI 对话做不到的（需要切到管理端页面）：**

- 确认领取设备 → 去 /admin/device 点按钮
- 取消申领 → 同上
- 归还设备 → 同上
- 管理员审批采购 / 确认到货 / 确认提货 / 确认入库 → 去 /admin/manage 和 /admin/devices

## 测试时快速验证 SQL

```sql
-- 看最新申领单状态
SELECT request_no, user_id, device_type, status, stock_status,
       allocated_device_id, purchase_order_no, created_at, completed_at
FROM admin_device_request ORDER BY id DESC LIMIT 3;

-- 看 DAG 每个节点的执行情况（核心亮点）
SELECT request_no, current_node, status, created_at
FROM sys_dag_execution
WHERE request_no = '<刚生成的单号>'
ORDER BY id;
-- 状态码对照：1=执行中, 2=成功, 3=失败, 4=挂起

-- 看库存变化
SELECT * FROM admin_device_inventory;

-- 看设备分配
SELECT id, device_type, sn, status, assigned_user_id, assigned_at
FROM admin_device_detail ORDER BY id DESC LIMIT 5;

-- 看采购单
SELECT * FROM admin_purchase_request ORDER BY id DESC LIMIT 3;
```

status 对照：申领单 1=待处理, 2=采购中, 3=准备中, 4=待领取, 5=已完成, 6=已取消；采购单 1=待审批, 2=已批准, 4=已到货, 5=已取消；DAG节点 1=执行中, 2=成功, 3=失败, 4=挂起。

```powershell
        [PSCustomObject]@{ User = "UserA"; Status = "ERROR"; Data = $_.Exception.Message }
    }
} -ArgumentList $baseUrl, $headersA, $body

$jobB = Start-Job -ScriptBlock {
    param($url, $hdr, $bdy)
    try {
        $response = Invoke-RestMethod -Uri "$url/api/device/request" -Method POST -Headers $hdr -Body $bdy -TimeoutSec 10

    } catch {
        [PSCustomObject]@{ User = "UserB"; Status = "ERROR"; Data = $_.Exception.Message }
    }
} -ArgumentList $baseUrl, $headersB, $body

Wait-Job $jobA, $jobB -Timeout 15 | Out-Null
Receive-Job $jobA | Format-List
Receive-Job $jobB | Format-List
Remove-Job $jobA, $jobB -Force
```

### 附：「AI 展示设备ID与实际分配不一致」排查过程

| 单号 | AI 展示的 ID | 实际分配的 ID | 数据库是否存在 |
| --- | --- | --- | --- |
| DEV-20260806-002 | ID:15 | 12 | id=15 未知 |
| DEV-20260806-006 | ID:16 | 13 | id=16 未知 |
| DEV-20260806-007 | ID:17 | 13 | Empty set |

规律：AI 展示的 ID 是 15 → 16 → 17 递增，与数据库真实分配完全无关。

排查三步：

1. **查数据库**：`SELECT * FROM admin_device_detail WHERE id = 17;` → Empty set。结论：id=17 在数据库中根本不存在。
2. **查后端代码**：`DeviceTools.requestDevice` 返回给 LLM 的文案是「分配设备 → 安装系统 → ……」，代码里根本没有设备 ID。且此时 DAG 还没跑（异步触发），系统根本不知道会分到哪个设备。
3. **查 System Prompt**：已有的约束只有「严禁编造时间」，没禁设备 ID。

结论：这是 LLM 幻觉，不是后端代码 Bug。LLM 看到工具返回的步骤列表，「理解」这是一个步骤列表，但不知道这是模板文案（还没有具体设备ID），凭「常识」觉得应该有个设备 ID，于是自己造了一个，且在对话上下文中递增续写。详细分析见 [troubleshooting/07](../troubleshooting/07-三个深度问题排查记录.md) 问题三。
