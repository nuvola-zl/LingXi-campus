## 一、前置准备

### 数据库初始状态确认

测试前先查这几张表，记录初始数据作为基线：

```sql
-- 申领单
SELECT * FROM admin_device_request ORDER BY id DESC LIMIT 5;

-- 库存（记下 total_count / available_count）
SELECT * FROM admin_device_inventory;

-- 设备明细（记下 status=1 在库的设备 SN）
SELECT * FROM admin_device_detail;

-- 采购单
SELECT * FROM admin_purchase_request ORDER BY id DESC LIMIT 5;

-- 归还记录
SELECT * FROM admin_device_return ORDER BY id DESC LIMIT 5;

-- DAG 执行记录
SELECT * FROM sys_dag_execution ORDER BY id DESC LIMIT 20;
```

### 准备用户

需要两个账号：

- 普通用户（role=USER）：用于发起申领、确认领取、取消、归还
- 管理员（role=ADMIN）：用于审批采购、确认到货、确认提货、确认归还

### 前端页面核对

| 审批管理 | /admin/manage | 管理员 |

## 二、测试场景一：有库存 —— 完整正向流程（核心技术路径）

> 亮点：DAG 自动编排、悲观锁防并发、并行节点执行、DAG 幂等

| # | 操作 | 前端页面 | 预期结果 | 关注数据表及字段 |
| --- | --- | --- | --- | --- |
| 1 | 确认库存 | — | 记下某个 device_type 的 available_count >= 1 | admin_device_inventory.available_count |
| 2 | 普通用户登录，进入「设备申领」页，选择有库存的设备类型，填原因，点「提交申请」 | /admin/device → 申请设备 Tab | 返回申领单号 DEVxxx，提示「当前仓库有库存，系统正在自动处理」 | admin_device_request：新增一条，status=3(准备中), stock_status=1 |
| 3 | 等待 2-3 秒（DAG 异步执行），在「进度查询」Tab 输入单号查状态 | /admin/device → 进度查询 Tab | 状态变为「待领取」（status=4），显示已分配设备ID | admin_device_request.status 变为 4，allocated_device_id 有值 |
| 4 | 查 DAG 执行记录 | — | 所有节点执行成功 | sys_dag_execution：checkInventory / branchByStock / allocateDevice / installSystem / configPermission / notifyPickup 都有 status=2(成功) 记录 |
| 5 | 验证库存扣减 | — | available_count 减 1 | admin_device_inventory.available_count 比步骤1少1 |
| 6 | 验证设备分配 | — | 对应设备 status=2(已分配)，assigned_user_id 指向当前用户 | admin_device_detail.status=2, assigned_user_id=当前用户ID |
| 7 | 用户点击「确认领取」 | /admin/device → 我的设备 Tab | 提示成功 | admin_device_request.status=5(已完成), completed_at 有值 |

第 4 步是面试核心亮点：展示 sys_dag_execution 表，说明每个节点都有执行记录、支持幂等重入、installSystem 和 configPermission 是并行执行的。

## 三、测试场景二：无库存 —— 采购挂起 + 恢复（DAG 核心价值）

> 亮点：DAG 异步挂起/恢复、采购审批链、管理员介入点

| # | 操作 | 前端页面 | 预期结果 | 关注数据表 |
| --- | --- | --- | --- | --- |
| 1 | 选择库存为 0 的设备类型（或从未存在过的类型），提交申领 | /admin/device → 申请设备 | 返回单号，提示「当前仓库无库存，已自动发起采购申请」 | admin_device_request：status=2(采购中), stock_status=2 |
| 2 | 查进度 | 进度查询 Tab | 显示「采购审批中」，有关联采购单号 POxxx | admin_purchase_request：新增一条，status=1(待审批) |
| 3 | 验证 DAG 挂起 | — | WaitPurchaseNode 状态为挂起 | sys_dag_execution：createPurchase 成功，waitPurchase status=4(挂起) |
| 4 | 管理员登录，进入「审批管理」 | /admin/manage | 待审批列表中出现步骤1的采购单 | sys_approval_record 待确认 |
| 5 | 管理员审批通过采购单 | /admin/manage | 提示成功 | admin_purchase_request.status=2(已批准) |
| 6 | 管理员进入「设备管理」→「采购单管理」→ 点「确认到货」 | /admin/devices → 采购单管理 Tab | 提示成功 | admin_purchase_request.status=4(已到货), arrived_at 有值 |
| 7 | 查库存 | /admin/devices → 设备库存 Tab | 新设备类型出现，库存数 = 采购数量 | admin_device_inventory 新增或 total_count 增加 |
| 8 | 查设备明细 | — | 新 SN 号设备已入库（status=1） | admin_device_detail 新增记录 |
| 9 | 验证 DAG 恢复 | — | DAG 自动恢复到货后的分配流程 | sys_dag_execution：resume 后 allocateDevice/installSystem/configPermission/notifyPickup 全部成功 |
| 10 | 切回普通用户，查进度 | /admin/device → 进度查询 | 状态变为「待领取」 | admin_device_request.status=4, allocated_device_id 有值 |
| 11 | 用户确认领取 | 我的设备 Tab | 完成 | status=5 |

第 3、9 步是核心：演示 DAG 在「采购等待」这个长流程中挂起 5 分钟/5 天都能从断点恢复，状态不丢。

## 九、管理员操作兜底（无页面时）

如果管理端页面对应功能不可用，可直接调用接口或用 SQL 兜底：

Body: {"approved": true, "remark": "同意采购"}

-- 数据库直接审批（前端不可用时）
UPDATE admin_purchase_request

```

```

## 十、演示时的讲解要点

跑流程的时候可以边操作边讲这些点：

1. 提交申领时 →「提交后异步触发自研的轻量级 DAG 工作流引擎，不阻塞用户请求」
2. 看 sys_dag_execution 表 →「每个节点执行都有持久化记录，支持幂等重入，服务重启不会重复执行」
3. 无库存场景 →「DAG 在采购节点挂起，状态持久化到数据库，3 天后到货也能从断点恢复」
4. 并发分配 →「用 SELECT FOR UPDATE 悲观锁保证库存不会超卖」
5. 补偿任务 →「每 10 分钟扫描异常单子自动回收资源，每天凌晨自动回收超期未领设备」
