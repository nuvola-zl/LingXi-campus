# 前后端接口对齐修复记录：一次扫描揪出 10 处不匹配

> 项目：Haze-AI-Hub 前端（Vue 3）× 后端（Spring Boot）
> 主题：前端 API 层与后端接口的全面对齐修复，以及修复后确认的接口覆盖情况
> 说明：我发起这次排查是因为发现「IT 入口能查出 HR/行政的会话列表」。我让 AI 全面扫描前端所有 API 调用并与后端接口逐一比对，产出问题清单后我确认了修复方案。以下分析与修复内容借助 AI 工具完成，修复后已通过联调验证。

## 一、起因：一个肉眼可见的 Bug

现象：前端有三个入口（IT / HR / 行政），但在 IT 入口的会话列表里，能查出 HR 和行政的会话——会话列表没有按域隔离。

我判断这大概率不是孤立问题：如果会话列表这种基础接口都对不上，其他接口可能也有类似毛病。于是让 AI 对整个前端项目的 API 层做了一次全面扫描，逐接口与后端比对路径、参数格式、字段名。

## 二、修复清单（10 处）

| # | 文件 | 问题 | 修复内容 |
| --- | --- | --- | --- |
| 1 | api/chat.ts:79 | **核心 Bug——会话列表跨域混查**：`getChatHistory('IT')` 调用 `/ai/history/chat?type=IT`，但后端该端点无 type 筛选参数，导致 IT/HR/ADMIN 的会话全部混在一起 | 改为调用 `/ai/session/list?type=IT&pageSize=100`（后端有 type 过滤） |
| 2 | api/session.ts | 全部 CRUD 参数格式错误：createSession 传了无效的 userId；updateSession 用 JSON body 但后端用 @RequestParam；deleteSession 用 body 传参但后端用 @RequestParam；toggleSessionTop 缺少必填的 isTop 参数 | 全部改为 @RequestParam 风格的正确传参方式 |
| 3 | api/approval.ts | 审批接口字段名错误：前端发送 `{ approved, comment }`，后端 ApproveDTO 期望 `{ approved, remark }` | 全部 comment → remark |
| 4 | api/device.ts + DeviceRequestView.vue | 路径与参数均错误：请求 `/admin/device/apply` 但后端 DAG 控制器挂在 `/dag/device`；前端传了后端不需要的 quantity 字段 | 路径改为 `/dag/device/`，去掉 quantity |
| 5 | api/model.ts | 删除请求格式错误：DELETE /ai/models 用 body `{ data: { id } }` 传参，后端用 @RequestParam Long id | 改为 `{ params: { id } }` |
| 6 | api/ticket.ts + EngineerTicketView.vue | resolve 多余参数：前端传 `{ resolution }` body，后端 resolve 端点无 @RequestBody | 去掉 resolution 参数，简化 UI |
| 7 | KnowledgeBaseChatView.vue | **SSE 解析逻辑反了**：`startsWith('data:')` 的内容被跳过，恰好跳过了实际数据 | 按 `\n\n` 分块，解析 `data:` 前缀提取内容；处理流结束后的尾随 buffer |
| 8 | api/meeting.ts + MeetingRoomView.vue | 字段名不匹配：前端预订发送 `title`，后端 BookDTO 期望 `purpose` | 全局 title → purpose |
| 9 | LeaveRequestView.vue | 缺少必填字段 days：后端 LeaveServiceImpl 强制校验 days > 0，前端没传 | 根据 startDate/endDate 自动计算天数 |
| 10 | api/punch.ts + PunchCorrectionView.vue | 字段名/值均错误：前端发 `{ date, type: 'IN'/'OUT' }`，后端期望 `{ punchDate, punchType: 'miss_punch'/'late' }` | 字段名对齐，下拉选项改为「忘打卡/迟到」 |

其中第 7 条（SSE 解析逻辑反了）是最值得记录的：原代码看到 `data:` 前缀就 `continue`，等于把 SSE 协议里的有效载荷全部丢掉了——这类 bug 不读协议规范、只靠「页面能出字」是测不出来的。

## 三、无需前端修复的已知问题

| 问题 | 说明 |
| --- | --- |
| /api/ticket/list 和 /api/ticket/query | 后端 TicketController 是 stub 代码（硬编码 TEST_USER_ID = 1L，直接返回 String 而非 JSON），TicketListView.vue 调这两个接口会直接解析 JSON 报错。需要后端实现完整的 ticket 查询接口 |
| chatAPI.sendMessage 未发送 model 参数 | 后端 ChatController 接受 model 参数但 ChatServiceImpl 未使用，前端也从未把它加入 FormData。这是个死参数，前后端都是 |

## 四、顺带发现的技术债

三个 ChatView（ItChatView.vue、HrChatView.vue、AdminChatView.vue）代码几乎一模一样，唯一区别是 domain 字符串（'IT'/'HR'/'ADMIN'）和欢迎文案/颜色。后续可以抽取为公共组件——已列入待办，未实施。

## 六、经验总结

1. 前后端分离开发中，「字段名不一致」和「传参格式不一致（body vs params）」是最高发的两类接口 bug，占本次 10 处问题的大多数；
2. 一个肉眼可见的 bug（会话混查）往往只是冰山一角，值得顺着它做一次全面扫描；
3. 管理端关键接口如果没有页面，要准备数据库兜底操作（例如采购审批也可以直接执行 SQL：`UPDATE admin_purchase_request SET status = 2, approved_by = <管理员ID>, approved_at = NOW() WHERE order_no = '<采购单号>';`，确认到货调用 `POST /admin/manage/purchase/{orderNo}/arrived`）。
