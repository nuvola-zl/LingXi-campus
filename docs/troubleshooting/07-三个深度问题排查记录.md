## 问题一：MyBatis-Plus `update-strategy: not_null` 导致 null 字段更新被静默忽略

### 问题现象

在设备申领系统中，取消申领、归还设备、补偿任务等场景需要将数据库字段更新为 NULL（如清空 `allocated_device_id`、`assigned_user_id`），但调用 `updateById()` 后数据库字段完全没有变化，且没有任何报错或日志告警。

### 问题原理

MyBatis-Plus 的 updateStrategy 有几种取值：

- `IGNORED`：全部字段都更新（包括 null）
- `NOT_NULL`：只更新非 null 字段（默认值）
- `NOT_EMPTY`：只更新非 null 且非空字符串的字段

项目中 application.yaml 配置了：

```yaml
mybatis-plus:
  global-config:
    db-config:
      update-strategy: not_null   # ← 全局配置
```

这意味着当实体对象调用 `setXxx(null)` 再 `updateById(entity)` 时，MP 在执行 SQL 之前会遍历所有字段，发现值为 null 就直接跳过，生成的 UPDATE SQL 中不包含该字段。

于是代码写的是「清空 allocated_device_id」，实际上 SQL 根本没执行。

### 问题严重性

这是一个非常隐蔽的 Bug：

1. 没有任何异常或日志，所有操作都返回成功
2. 单元测试如果只读实体对象会通过（内存中确实 set 为 null 了）
3. 只有查数据库才能发现字段没变
4. 导致后续逻辑错误连锁反应：补偿任务重复释放设备、库存计数虚增

### 有问题的代码示例

```java
// AdminDeviceRequest request = ...;
// 意图：清空已分配设备，让该设备回到可用状态
request.setAllocatedDeviceId(null);   // ← 被 MP 静默忽略
request.setStatus(6);
requestMapper.updateById(request);     // ← SQL 中不包含 allocated_device_id 字段
```

生成的 SQL 实际是：

```sql
UPDATE admin_device_request SET status = 6 WHERE id = ?
-- allocated_device_id 字段根本没出现在 SQL 中！
```

### 修复方案

使用 `LambdaUpdateWrapper.set()` 强制写入 null，该方法绕过 updateStrategy 检查：

```java
// 修复后：LambdaUpdateWrapper 强制 set null
LambdaUpdateWrapper<AdminDeviceRequest> wrapper = new LambdaUpdateWrapper<>();
wrapper.eq(AdminDeviceRequest::getId, request.getId())
        .set(AdminDeviceRequest::getStatus, 6)
        .set(AdminDeviceRequest::getAllocatedDeviceId, null);  // ← 强制写入 null
requestMapper.update(null, wrapper);
```

生成的 SQL：

```sql
UPDATE admin_device_request
SET status = 6, allocated_device_id = NULL
WHERE id = ?
```

### 涉及的修复文件

- `DeviceUserController.java`：cancelAllocated() 方法
- `DeviceCompensationService.java`：compensate() 方法
- `DeviceTimeoutJob.java`：autoRecycle() 方法
- `AdminManageController.java`：confirmReturn() 方法

### 知识点总结

1. MyBatis-Plus 的 updateStrategy 是全局策略，影响所有 updateById/update 调用
2. `LambdaUpdateWrapper.set(field, null)` 不受 updateStrategy 限制
3. 配置 `update-strategy: not_null` 时要特别注意 null 更新的场景
4. 凡是需要「清空」某个字段的业务，都应该用 LambdaUpdateWrapper 而非实体 updateById

## 问题二：DAG 并行执行节点导致 HashMap 线程不安全 → 空指针异常

### 问题现象

DAG（有向无环图）工作流引擎在执行设备申领流程时，installSystem 和 configPermission 两个节点被并行执行。configPermission 节点偶尔抛出 NullPointerException：

```text
java.lang.NullPointerException
  at top.lingxi.campus.common.context.DagContext.toJson(DagContext.java:46)
```

错误不稳定复现，只在并发争用时出现。

### DAG 工作流背景

设备申领 DAG 流程中有 5 个节点：

```text
checkInventory → branchByStock → allocateDevice
                                    ↓
                  ┌─────────────────┴──────────────────┐
                  ↓                                     ↓
            installSystem                        configPermission
                  ↓                                     ↓
                  └─────────────────┬──────────────────┘
                                    ↓
                             notifyPickup
```

其中 installSystem 和 configPermission 没有依赖关系，DAG 引擎会将它们分配到线程池中并行执行，以提升处理速度。两个线程都会往 `DagContext.results` 这个 Map 中写入自己的执行结果。

### 问题原理

DagContext 中 results 字段原来声明为普通的 HashMap：

```java
private Map<String, NodeResult> results = new HashMap<>();
```

HashMap 是线程不安全的。当多个线程并发执行 put() 操作时：

1. 可能导致内部数组链表成环（put 时发生 resize 争用）
2. 后续 get()/遍历读到不一致的内部状态
3. toJson() 遍历 entrySet 时，一个线程在 put 修改结构，另一个在遍历，触发 ConcurrentModificationException 或读到脏数据导致 NPE

toJson() 方法中的遍历代码：

```java
for (Map.Entry<String, NodeResult> entry : results.entrySet()) {
    NodeResult nodeResult = entry.getValue();
    if (nodeResult == null) continue;  // ← 之前没有这个防御
    // ... 读取 nodeResult.isSuccess() 等
}
```

在并发 put 的情况下，`entry.getValue()` 可能返回 null，直接调用 `nodeResult.isSuccess()` 就抛出了 NPE。

### 有问题的代码

```java
@Data
public class DagContext {
    private String requestNo;
    private Map<String, Object> params;
    private Map<String, NodeResult> results;  // ← HashMap，非线程安全

    public DagContext(String requestNo, Map<String, Object> params) {
        this.requestNo = requestNo;
        this.params = params != null ? params : new HashMap<>();
        this.results = new HashMap<>();        // ← 普通 HashMap
    }

    public void putResult(String nodeId, NodeResult result) {
        results.put(nodeId, result);           // ← 并发 put，不安全
    }

    public String toJson() {
        // ...
        for (Map.Entry<String, NodeResult> entry : results.entrySet()) {
            NodeResult nodeResult = entry.getValue();
            Map<String, Object> r = new HashMap<>();
            r.put("success", nodeResult.isSuccess());  // ← NPE 发生点
            // ...
        }
    }
}
```

### 修复方案

```java
@Data
public class DagContext {
    private String requestNo;
    private Map<String, Object> params;
    private Map<String, NodeResult> results;

    public DagContext(String requestNo, Map<String, Object> params) {
        this.requestNo = requestNo;
        this.params = params != null ? params : new HashMap<>();
        this.results = new ConcurrentHashMap<>();  // ← 替换为 ConcurrentHashMap
    }

    public void putResult(String nodeId, NodeResult result) {
        results.put(nodeId, result);  // ← ConcurrentHashMap.put() 线程安全
    }

    public String toJson() {
        // ...
        for (Map.Entry<String, NodeResult> entry : results.entrySet()) {
            NodeResult nodeResult = entry.getValue();
            if (nodeResult == null) continue;  // ← 加 null 防御，双重保险
            Map<String, Object> r = new HashMap<>();
            r.put("success", nodeResult.isSuccess());
            // ...
        }
    }
}
```

### 知识点总结

1. ConcurrentHashMap 使用分段锁（JDK7）或 CAS + synchronized（JDK8+）实现线程安全
2. ConcurrentHashMap 的 iterator 是弱一致性的，遍历时不会抛 ConcurrentModificationException
3. 在并行/异步场景中，共享可变状态必须使用线程安全的容器
4. HashMap 在并发 put 时可能导致 CPU 100%（死循环），这是经典面试题
5. toJson() 是读操作，但也要防御 null——因为 ConcurrentHashMap 不支持 null key/value

## 问题三：LLM 函数调用中的「幻觉」——大模型编造不存在的设备 ID

### 问题现象

用户通过 AI 对话界面测试设备申领流程时，LLM 会「报告」一些设备 ID（如 15、16、17），但实际数据库中只有 ID 为 1-14 的设备。这些 ID 看起来非常合理（自增连续），用户如果不查数据库根本无法发现 LLM 在编造数据。

### 问题原理

这是大语言模型（LLM）的「幻觉」（Hallucination）问题：

1. 系统通过 Spring AI 的 ChatClient + Tools（函数调用）将后端 API 注册为 LLM 可调用工具
2. 用户问「我的设备是什么状态」，LLM 调用工具获取数据
3. 工具返回真实数据，但 LLM 在生成回答时可能「脑补」额外的设备 ID
4. LLM 本质是概率模型，它会根据训练数据中常见的模式（连续自增 ID）来补全它「认为」合理但实际不存在的信息

### 具体的幻觉案例

后端工具返回的数据：

```json
{
  "requestNo": "DEV-20260806-001",
  "allocatedDeviceId": 3,
  "deviceType": "笔记本电脑"
}
```

LLM 生成的回答：

```text
"您的设备已分配，设备ID为15，当前状态为待领取。另外设备16和17也在处理中..."
                            ↑↑               ↑↑   ↑↑
                       完全是编造的，与后端返回数据不符
```

我在回归测试中又抓到一组更有说服力的证据：

| 单号 | AI 展示的设备 ID | 数据库实际分配的 ID | 数据库是否存在该 ID |
| --- | --- | --- | --- |
| DEV-20260806-002 | 15 | 12 | id=15 未知 |
| DEV-20260806-006 | 16 | 13 | id=16 未知 |
| DEV-20260806-007 | 17 | 13 | Empty set |

规律很明显：AI 展示的 ID 是 15 → 16 → 17 递增，与数据库真实分配完全无关——它在根据上下文「续写」数字。

我当时的排查路径是：第一步查数据库确认 `id=17` 根本不存在（Empty set）；第二步读 `DeviceTools.requestDevice` 源码，确认后端返回给 LLM 的文案是「分配设备 → 安装系统 → ……」，里面根本没有设备 ID；第三步检查 System Prompt，发现只有「严禁编造时间」的约束，没有约束其他字段。三步下来，根因锁定为 LLM 幻觉而非后端 bug。

### 为什么这是个「有意思」的问题

1. 常规的反幻觉手段（如 system prompt 中写「不要编造时间」）只解决了时间幻觉，但 LLM 可能在任意字段上产生幻觉（ID、数量、状态等）
2. 设备 ID 是客观事实，不像时间有明确的当前值可以注入 prompt
3. 用户看到连续且合理的数据（15, 16, 17）很难怀疑是假的
4. 这在面试中能展示对 AI 应用开发中实际挑战的理解

### 当前缓解措施

System Prompt 中已有的约束：

```text
"- 绝不编造时间信息（如当前时间、创建时间等）"
```

但这只约束了时间，没有约束其他数据字段。

### 可能的修复方向（尚未实施）

1. **强化 System Prompt**：将约束扩展为「只使用工具返回的数据，不要编造任何具体数值、设备ID、状态、时间等。如果工具没有返回某个字段，直接说『未获取到』」
2. **数据校验层**：在 LLM 响应返回给用户之前，用正则/规则校验响应中的关键数值（如设备ID）是否在工具返回数据中出现过
3. **结构化输出**：让 LLM 只返回工具调用结果的直接摘要，不添加任何「合理推测」
4. **对比展示**：同时给用户展示「原始数据」和「AI 解读」，让用户自行对比
5. **二次确认机制**：对于关键操作，加入确认步骤，确认时展示原始数据而非 AI 总结

暂缓修复的原因：当时优先保证功能链路稳定，且该问题只影响展示文案、不影响真实数据；候选方案已记录，后续按优先级实施。

### 知识点总结

1. LLM 幻觉是函数调用/Tool Use 模式中的核心挑战，所有大模型都有这个问题
2. 幻觉不仅限于时间，任何 LLM「觉得合理」的数值、ID、顺序都可能被编造
3. 生产级 AI 应用需要多层防护：Prompt 约束 + 输出校验 + 人工确认关键操作
