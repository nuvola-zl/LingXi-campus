# 工单分类匹配方案设计：从硬编码关键词到三层降级策略

> 项目：Haze-AI-Hub · IT 工单模块
> 状态：**方案设计**（三个方案已完成对比分析，推荐组合策略已确定；具体实施进度见文末「待办与演进方向」）

## 一、当前问题

`matchCategory` 方法用硬编码关键词（邮箱 / vpn / 电脑 / 蓝屏等）匹配工单分类，存在三个硬伤：

1. **维护困难**：新增分类或关键词必须改代码、重新发版；
2. **扩展性差**：关键词列表随着业务增长无限膨胀；
3. **无法理解语义相似表达**：「笔记本坏了」和「电脑蓝屏」在用户看来是同一类问题，但关键词匹配看不出来。

## 二、候选方案

### 方案一：数据库动态关键词（短期过渡）

**核心思路**：把关键词从代码里抽出来，放到 `biz_service_catalog.trigger_keywords` 字段（JSON 数组），启动时加载到内存，匹配时遍历。

**实现要点**：

- 启动时 `SELECT * FROM biz_service_catalog` 加载所有 trigger_keywords
- 用户输入后，遍历所有目录的关键词做 contains 匹配
- 命中则返回对应 category_id

**优点**：运营人员直接在数据库配关键词，不用改代码发版。

**缺点**：还是关键词匹配，无法理解「笔记本坏了」和「电脑蓝屏」是同一个分类。

### 方案二：向量语义相似度匹配（中期推荐）

**核心思路**：利用现有 pgvector + text-embedding-v4，把服务目录描述向量化，用户输入也向量化，做语义检索取 Top1。

**实现要点**：

- 初始化时把 biz_service_catalog 的 name + description 生成向量，存入 kb_chunk 或单独一张表
- 用户输入后，调 text-embedding-v4 生成向量
- SQL 用 `ORDER BY embedding <=> ? LIMIT 1` 查最相似的服务目录
- 取到 category_id 返回

**优点**：

- 不需要关键词，语义相近就能匹配（「电脑蓝屏」≈「笔记本坏了」≈「系统崩溃」）
- 基础设施已有（PG + pgvector + embedding 模型）

**缺点**：

- 需要预先向量化服务目录数据
- 冷启动时向量库为空需要处理

### 方案三：大模型直接输出分类（长期最智能）

**核心思路**：改 EXTRACT_PROMPT，让 AI 在提取 description / priority / title 的同时，直接输出 categoryId。

**实现要点**：

Prompt 里增加字段说明：

```text
"categoryId": 1(IT运维) 或 2(人力资源) 或 3(行政服务) 或 4(财务服务)
```

解析 JSON 时读取 categoryId。兜底：如果 AI 没返回 categoryId 或超时，降级到方案二（向量匹配）或方案一（数据库关键词）。

**优点**：

- 最智能，能理解复杂语义和上下文
- 零维护，不需要配关键词或向量库

**缺点**：

- 每次都要调大模型，有 API 成本和延迟
- 模型可能「幻觉」输出不存在的分类 ID

## 三、推荐组合策略（最终形态）

```text
用户输入
    ↓
【第一层】大模型提取（方案三）
    ├─ 成功返回 categoryId → 直接建单
    └─ 失败/超时
            ↓
【第二层】向量相似度匹配（方案二）
    ├─ 相似度 > 阈值 → 返回 categoryId
    └─ 相似度 < 阈值 或 向量库未初始化
            ↓
【第三层】数据库关键词兜底（方案一）
    ├─ 命中关键词 → 返回 categoryId
    └─ 未命中 → 追问用户「请问这是 IT/HR/行政问题？」
```

## 四、设计考量

三层降级的核心逻辑是「按成本和智能程度排序」：大模型最聪明但最贵最慢，放第一层；向量匹配成本中等、能理解语义，做第二层；关键词最便宜但最笨，只做兜底。任何一层失效都不影响整体可用性——这也是整个项目的设计原则之一：**LLM 负责智能，代码负责兜底**。
