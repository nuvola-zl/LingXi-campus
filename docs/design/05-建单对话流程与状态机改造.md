> 项目：Haze-AI-Hub · IT 工单模块
> 主题：建单对话的产品形态设计、多轮状态机改造记录、知识反馈闭环的取舍、联调中发现的问题清单
> 状态：状态机改造已实施（改动由 AI 工具执行，经我逐条审查确认）；文末问题清单中各项状态已标注

## 一、产品意图：我要的建单对话是什么样的

前端有三个 AI 入口：IT、HR、行政，用户在不同界面进行不同域的询问。当前设计聚焦 IT 域。我想要的体验是：用户很清楚自己是 IT 问题，就来 IT 入口询问，之后对话能自然分流到三种情况：

1. **检索不到相关知识** —— AI 答复「没找到类似方案」，主动引导「我帮你建个工单吧」，用户确认后收集详细描述；过程中用户随时可以说「算了」取消建单。
2. **检索到知识，但没解决** —— AI 先给出排查建议；用户说「试了还是不行」，AI 再引导建单、收集描述；途中同样可以正常取消。
3. **检索到知识，解决了** —— 用户对 AI 说「解决了」「谢谢」，对话自然结束，不产生工单。

另外还有一种直接进入界面就说「帮我建个工单」的情况，AI 直接询问问题描述。

一句话总结我的目标：**希望它能像一个真正的人一样洞察用户意图，干对的事情**——而不是一个死板的表单收集器。

升级后的完整对话链路示例：

```text
用户：VPN 怎么连接不上了
    ↓
AI（内部检索知识库 top-3）：
    "VPN 连接失败 809 错误 → 检查防火墙设置 → 允许 IKEv2 流量"
    "VPN 809 → 重启 IPSec 服务"
    "VPN 无法连接 → 检查预共享密钥"
    ↓
AI 回复：
    "根据知识库，VPN 错误 809 通常由以下原因导致：
     1. 防火墙阻止 IKEv2 流量
     2. IPSec 服务未启动
     3. 预共享密钥错误

     建议尝试：
     1. 检查 Windows 防火墙，允许 IKEv2
     2. 运行 services.msc 重启 IPSec
     3. 确认预共享密钥是否正确

     如果尝试后仍无法解决，我可以帮您创建工单。"
    ↓
用户：试过了，还是不行
    ↓
AI：好的，已为您创建工单，工程师会优先处理。
```

## 二、状态机改造：实施内容

> 以下改动方案由我与 AI 协作完成：我描述清楚目标流程和边界情况后，让 AI 实施代码修改，再逐条审查它的改动清单并验证。以下为 AI 给出的修改总结，经我核对确认与实际改动一致。

### 修改清单

**1. TicketCreateState.java —— 新增 sessionId 字段**

添加 `private Long sessionId;` 字段，用于记录状态属于哪个会话，Handler 层用这个字段做脏状态校验。

**2. TicketCreateHandler.java —— 三处修改**

- `supports()`：校验 state 的 sessionId 是否匹配当前会话，不匹配就不拦截（让常规流程走）。
- `handle()`：
  - 检测到 CONFIRM 状态时，委托给 continueCreate 处理确认/取消；
  - 检测到脏状态（sessionId 不匹配）时，先清理旧状态再走新建单流程；
  - 新建单时先调用 `abandonCreate()` 清理可能残留的脏状态。

**3. TicketCreateServiceImpl.java —— 核心修改**

| 修改点 | 说明 |
| --- | --- |
| startDirectCreate | 增加 sessionId 参数，保存到 state |
| startSuggest | 保存 sessionId 到 state |
| handleIntent case "ticket_create" | 不再自动创建工单。无论主动/非主动路径，统一清空描述、反问用户 |
| continueCreate（前半） | 新增 CONFIRM 状态处理：识别用户的「确认」/「取消」 |
| continueCreate（后半） | 收集完描述后进入 CONFIRM 状态而非直接创建 |
| cleanThinkTags | 修复正则：从损坏的 `(?s) t...d .*? d` 改为正确的 `<think>` `<thinking>` `<thought>` 标签匹配 |

**4. `<think>` 标签清理 —— 修复损坏的正则**

| 文件 | 修改 |
| --- | --- |
| DefaultChatHandler.removeThinkTags | `t...d` → `<think>` |
| ChatPipeline.extractThinkContent | `indexOf("t...d")` → `indexOf("<think>")`，字符串长度 6→7 |
| ChatPipeline.wrap() 过滤条件 | `contains("t...d")` → `contains("<think>")` |
| TicketCreateServiceImpl.cleanThinkTags | 统一方法，匹配 3 种格式 |

### 改造后的完整流程

```text
用户描述问题 → AI 检索知识库 →
  ├─ 没找到 → 「没找到方案，帮你建工单吧」→ 问描述 → 确认 → 创建
  ├─ 找到了 → 给建议 → 用户说「谢谢/解决了」→ 取消
  └─ 找到了 → 给建议 → 用户说「没解决」→
       ├─ 「帮你建工单，请描述具体问题？」→ 收集描述 → 确认 → 创建
       └─ 用户说「创建工单」→「请描述具体问题？」→ 收集 → 确认 → 创建
```

每次新会话开始时，会自动清理 Redis 中该用户之前残留的旧状态，不会出现跨测试污染。

### 我对改动方式的一个要求

我要求 AI 把原始代码注释保留（`// ===== 原代码（保留供参考）=====`），方便我对比调试。这是我在 AI 协作中形成的一个习惯：**大改动必须留对照，确认无误后再清理**。

## 三、知识反馈闭环的取舍：为什么先做工程师侧

当时面临一个排序问题：先做「AI 自动把工单沉淀为知识库」，还是先做工程师接单/处理流程。我的判断是**等工程师侧做完再做**（选择 A）。

理由：等有了工程师处理记录，比如：

```text
[工程师小李] 已重置密码，请使用初始密码 <初始密码占位符> 登录
[用户] 可以登录了，谢谢
[工程师] 关闭工单
```

这时候 AI 总结出来的知识库文档才有价值，例如：

> 《邮箱账号锁定解锁流程》：1. 确认账号状态 2. 管理员后台重置密码 3. 通知用户使用初始密码登录并修改

如果缺少工程师的处理过程，AI 只能总结用户的提问，沉淀不出真正可复用的解决方案。所以结论是：先做工程师接单/处理/更新状态，再回头做知识沉淀。
